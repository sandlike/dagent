# Dagent 需求评审增补（2026-07-30）

> 状态：待评审
> 适用范围：`dagent-web`、`dagent-backend`、`dagent-agent`、`dagent-wiki`
> 依据：2026-07-30 口述需求、流程截图、现有 PRD v2.1 与代码骨架
> 原则：本文件先记录本轮增量，不直接覆盖 PRD v2.1；评审通过后合并为 PRD v2.2。

## 1. 本轮结论摘要

1. 新增 **API 网关管理**，统一管理 OpenCode 使用的模型 API、Token 预算、优先级和故障切换。
2. MVP 默认提供两个职责型 Agent：
   - **需求描述与需求澄清 Agent**
   - **开发 Agent**
3. 用户选择的是同一职责下的 Agent 风格/配置，不允许把需求澄清 Agent 用于代码开发。
4. 目标流程调整为：需求描述与澄清 -> 开发文档 -> 研发 -> 研发报告人工确认 -> 测试用例人工确认 -> 测试执行 -> 最终人工验收。
5. 开发文档被驳回时，按本轮口述的最新规则回到 **需求描述**，携带驳回意见重新澄清。
6. 每个职责型 Agent 使用独立 Docker 容器。算力不是约束时，为降低恢复和回退复杂度，容器在最终验收前不销毁；人工等待期间保持空闲或停止但保留工作卷。

## 2. 名词统一

| 名词 | 定义 | 边界 |
|---|---|---|
| 项目空间（Project） | 一组代码仓库、需求和 Agent 运行上下文的逻辑容器 | 不是传统项目管理系统，不承载迭代、看板和成员排期 |
| 需求（Requirement） | 针对一个项目空间提出的一项具体功能、修复或改造 | 每个需求独立运行一条流水线 |
| Agent 定义 | 一个稳定的职责类型，如需求澄清、开发 | 决定可使用的 Skill、MCP、权限和可选风格 |
| Agent 配置/风格 | 同一职责下的具体行为模板 | 用户可选；未选择时使用默认配置 |
| Agent 实例 | 某个需求运行时创建的容器和 OpenCode 会话 | 有明确生命周期和所属需求，不能跨租户复用 |
| 开发文档 | 澄清后生成、供人工确认的技术方案 | 与现有 PRD 中的“方案文档/技术方案”是同一产物，后续统一显示为“开发文档（技术方案）” |

## 3. API 网关管理

### 3.1 目标

OpenCode 只连接一个由 Dagent 管理的 OpenAI-compatible 网关地址。网关再根据模型、优先级、预算和健康状态选择上游 API，避免把密钥切换和 Token 统计分散到各 Agent 容器。

### 3.2 MVP 配置模型

| 字段 | 说明 |
|---|---|
| `name` | API 配置名称 |
| `provider` | 上游服务商或兼容协议类型 |
| `base_url` | 上游 API 地址 |
| `api_key_secret_ref` | 密钥引用，只保存密钥管理系统中的引用，不在数据库明文保存 |
| `model_mapping` | Dagent 模型别名到上游模型 ID 的映射 |
| `priority` | 路由优先级，数值越小越优先 |
| `token_budget` | 可分配 Token 总预算；第一优先级初始值为 50,000 |
| `token_used` | 已结算 Token |
| `token_reserved` | 并发请求已预留但尚未结算的 Token |
| `status` | `active` / `exhausted` / `degraded` / `disabled` |
| `timeout_seconds` | 单次调用超时 |
| `max_retries` | 在同一上游上的重试次数 |

> 这里的 50,000 Token 是 **API 配额预算**，不是模型上下文窗口大小，前后端字段和文案不得混用。

### 3.3 优先级与切换规则

1. 第一优先级 API 配置 50,000 Token 预算；第二优先级配置充足预算。
2. 请求进入时，网关按 `priority ASC` 选择支持目标模型且状态可用的 API。
3. 发起请求前原子预留预计 Token，避免并发请求同时穿透 50,000 上限。
4. 请求完成后按上游返回的实际 `prompt_tokens + completion_tokens` 结算，多退少补。
5. 第一优先级剩余预算不足时，不再接收新请求，自动转到第二优先级。
6. 上游返回限流、配额耗尽、可重试的 5xx 或超时时，可以按策略切换到下一优先级。
7. 参数错误、内容安全拒绝等非重试错误不得盲目切换，避免重复计费和隐藏真实错误。
8. 每次切换必须记录：需求、Agent 实例、模型、原 API、目标 API、原因、重试次数和 Token 用量。

### 3.4 验证场景

| 场景 | 预期结果 |
|---|---|
| 第一优先级尚有足够预算 | 请求只调用第一优先级 |
| 第一优先级预算刚好耗尽 | 当前请求正常结算，后续请求使用第二优先级 |
| 多个并发请求接近 50,000 上限 | 预留总量不越界，超出部分进入第二优先级 |
| 第一优先级返回 429/配额耗尽 | 按策略切到第二优先级，并产生切换审计记录 |
| 第一优先级返回 400 参数错误 | 不切换，向上返回可诊断错误 |
| 第二优先级也不可用 | Agent 任务进入可恢复失败，允许人工重试，不丢流水线状态 |

## 4. Agent 管理

### 4.1 产品含义

“Agent 管理”不是管理聊天机器人列表，而是管理 **职责模板、配置版本和运行实例**：

- Agent 定义：职责边界和允许执行的阶段。
- Agent 配置：模型、Prompt、风格、Skill、MCP 和权限。
- Agent 版本：发布后不可变，运行中的需求固定引用版本，避免配置更新导致结果不可复现。
- Agent 实例：需求运行时的容器、会话、状态和日志。

### 4.2 两个默认 Agent

#### A. 需求描述与需求澄清 Agent

职责：理解原始需求、分析代码库影响、提出澄清问题、整理验收标准并生成开发文档草稿。

默认风格：`balanced`，在信息充分性和交互轮次之间平衡。

可选风格：

| 风格 | 行为 |
|---|---|
| `balanced`（默认） | 每轮只问影响决策的关键问题，输出结构化需求和验收标准 |
| `concise` | 尽量减少问题数量，适合小改动 |
| `rigorous` | 强调边界条件、权限、兼容性、异常路径和非功能指标 |

建议 Skill：

- `requirement-elicitation`：识别目标、范围、角色、约束、异常路径和未决项。
- `codebase-impact-analysis`：只读分析仓库结构、相关模块和变更影响面。
- `acceptance-criteria`：把自然语言转成可验证的验收标准与 Definition of Done。
- `development-spec`：生成统一模板的开发文档（技术方案）。

建议 MCP/工具：

- 项目仓库：优先使用 OpenCode 内置 `read`、`grep`、`list` 和受限 Git CLI，保持只读。
- Team/Codeup：建设项目专用 MCP，MVP 只开放需求读取、评论写入、状态读取等最小工具。
- Context7：需要核对第三方库官方文档时按需启用，不默认加载所有工具。
- 禁止代码编辑、Git push、部署、数据库写入和任意 shell。

#### B. 开发 Agent

职责：依据已确认开发文档创建分支、修改代码、执行检查、生成研发报告、生成测试用例、执行测试并修复失败。

默认风格：`balanced`，以正确性、最小改动和可验证性为优先。

可选风格：

| 风格 | 行为 |
|---|---|
| `balanced`（默认） | 完整实现并运行与风险相称的测试 |
| `conservative` | 最小改动，优先兼容性，不做无关重构 |
| `rapid` | 面向原型快速交付，但仍必须通过最低质量门槛 |

建议 Skill：

- `implementation-planning`：把开发文档映射为文件级改动计划和检查清单。
- `code-change`：遵循仓库规范实施小范围修改。
- `test-design`：先生成测试用例与验收映射，再等待人工确认。
- `test-execution-and-debugging`：执行测试、定位失败并在限制次数内修复。
- `code-review`：按功能、边界、安全、兼容性和维护性复核变更。
- 前端项目可按许可证评估后复用 Anthropic 的 `frontend-design`、`webapp-testing`；不得无许可证审查地整包复制第三方 Skill。

建议 MCP/工具：

- 项目仓库：OpenCode 内置编辑工具、受控 shell 与 Git CLI。
- Playwright：仅当前端/E2E 任务需要时启用，避免长期占用上下文。
- Context7：按需查询依赖库官方文档。
- Team/Codeup：允许回写研发报告、测试报告和交付状态；创建 PR 仍优先走现有 Git CLI/平台适配层。
- `git push`、外部目录访问、部署和破坏性命令必须经过策略审批。

### 4.3 前端选择规则

1. 系统根据流水线阶段自动选择 Agent 职责，用户不能跨职责选择。
2. 用户可以在创建需求时选择“需求澄清风格”，未选择时使用默认值。
3. 开发文档确认前，用户可以选择“开发风格”，未选择时使用默认值。
4. Agent 下拉框只展示当前阶段兼容的配置，并显示默认标记、版本、模型和简短风格说明。
5. 配置一旦用于某条需求，流水线记录具体版本；管理员后续发布新版本不会改变运行中的需求。

### 4.4 OpenCode 配置原则

- 使用 `.opencode/agents/` 定义职责型 Agent，使用 `.opencode/skills/<name>/SKILL.md` 放置项目 Skill。
- 通过 Agent 级权限区分只读需求 Agent 与可编辑开发 Agent。
- MCP 默认全局关闭，再按 Agent 显式开启，降低上下文占用和越权风险。
- OpenCode 原生支持会话中切换 Primary Agent，但 Dagent 前端应通过职责约束包装该能力，不能把无效组合暴露给普通用户。

## 5. 目标业务流程

完整流程见[目标业务流程图](../architecture/figures/dagent-target-workflow.md)。

| 阶段 | 主要执行者 | 核心产物 | 人工门禁/回退 |
|---|---|---|---|
| 需求描述 | 用户 + 需求 Agent | 原始需求、目标、范围 | 用户提交 |
| 需求澄清 | 需求 Agent + 用户 | 澄清记录、结构化需求、验收标准 | 信息不足可多轮澄清 |
| 开发文档生成 | 需求 Agent | 开发文档（技术方案） | 进入人工确认 |
| 开发文档确认 | 用户 | 已批准开发文档 | 驳回时填写意见，回到需求描述 |
| 研发实现 | 开发 Agent | 代码变更、分支、提交、检查清单 | 失败可重试/人工接管 |
| 研发报告确认 | 开发 Agent + 用户 | 研发报告、变更摘要、自检结果 | 驳回回到研发实现 |
| 测试用例生成 | 开发 Agent | 测试用例、预期结果、验收映射 | 生成后等待人工确认 |
| 测试用例确认 | 用户 | 已批准测试集 | 驳回回到测试用例生成 |
| 测试执行 | 开发 Agent/测试执行器 | 测试报告、日志、覆盖率 | 失败回到研发实现 |
| 最终验收 | 用户 | 验收结论、交付清单 | 只有明确点击确认后才完成 |

### 5.1 最终确认要求

- 测试通过不能自动把需求标记为完成。
- 页面必须展示最终交付清单：需求文档、澄清记录、开发文档、代码/PR、研发报告、测试用例、测试报告。
- 用户勾选清单并点击“确认验收”后才进入 `completed`。
- 确认接口必须幂等，并记录确认人、时间、产物版本和确认意见。
- “100% 确认”应表达为确定性的人工动作，不使用模型置信度百分比。

## 6. Agent 容器生命周期

完整生命周期见[Agent 容器生命周期图](../architecture/figures/dagent-agent-container-lifecycle.md)。

### 6.1 推荐方案：按需求保留到最终验收

1. 需求进入澄清时创建 **需求 Agent 容器**，挂载该需求独享的工作卷。
2. 开发文档确认后创建 **开发 Agent 容器**；需求 Agent 容器转为空闲，但暂不销毁。
3. 人工确认期间，容器可以保持运行；若需降低资源占用，可停止容器，但必须保留工作卷、OpenCode 会话标识和检查点。
4. 任一回退阶段优先复用原容器和会话，避免重新 clone、重新索引和丢失上下文。
5. 只有最终验收完成、需求取消，或超出明确的归档 TTL 后，才归档产物并销毁容器与临时工作卷。

选择该方案的原因：本项目明确不以算力为主要约束，保留容器能最大程度减少跨阶段交接、长时间人工等待和流程回退时的恢复故障。

### 6.2 不能只依赖容器保存状态

即使容器保留到最后，以下状态仍必须外置：

- 后端数据库：流水线状态、审批记录、Agent 版本、容器 ID、会话 ID、Token 用量。
- 对象存储/制品库：开发文档、研发报告、测试用例、测试报告、日志归档。
- Git 远端：已确认的代码提交与分支。
- 独立工作卷：未提交工作区、OpenCode 会话缓存和临时测试产物。

目标是容器意外退出后可以重建，而不是把“容器不销毁”当成持久化方案。

### 6.3 销毁前置条件

- 最终验收已确认，或需求被明确取消。
- 所有要求保留的产物已上传并完成校验。
- Git 工作区无未归档的重要变更。
- Agent 日志和 Token 用量已经结算。
- 后端已把实例状态标记为 `archived`。

## 8. 建议验收标准

### API 网关

- 能配置至少两个同模型上游并设置不同优先级和 Token 预算。
- 自动化测试证明第一优先级达到 50,000 Token 后切到第二优先级。
- 并发测试证明 Token 预留不会导致预算明显超发。
- 管理页面可查看健康状态、剩余额度、调用次数、失败数和切换记录。

### Agent 管理

- 系统内置两个不可删除但可停用/升级的默认 Agent 定义。
- 两个 Agent 的 Skill、MCP 和权限配置可独立版本化。
- 用户只能选择当前阶段允许的风格，未选择时使用默认配置。
- 每次执行可追溯到 Agent 配置版本、模型和 API 路由记录。

### 业务流程

- 三个人工确认点不可被 Agent 自动跳过：开发文档、研发报告、测试用例。
- 最终验收不可由测试通过自动触发。
- 所有驳回操作必须填写意见并保存审计记录。
- 回退后保留历史产物，新版本递增，不覆盖旧版本。

### 容器生命周期

- 人工等待后可从原会话继续执行。
- 容器异常退出后可从数据库、制品和工作卷恢复。
- 最终确认前不会自动清除仍可能用于回退的工作区。
- 最终销毁前执行归档校验，并可查询销毁记录。

## 9. 待评审问题

1. “开发文档驳回回需求描述”是否确定替换截图中“回方案生成”的标注？本文件按口述最新要求处理。
2. 最终验收驳回时，是固定回研发实现，还是由用户选择回研发实现/测试用例生成？建议默认回研发实现并允许选择目标阶段。
3. 50,000 Token 是每个 API 配置的永久总额度、按日/月重置额度，还是一次验收测试额度？数据模型需增加 `reset_policy`。
4. 需求 Agent 是否允许把澄清评论写回 Team 系统？建议允许，但继续禁止代码和仓库写入。
5. 容器长期等待的归档 TTL 建议先设 7 天还是 30 天？在“不考虑算力”的前提下建议 30 天，且超时前通知负责人。
